# ADR-001. Учёт в одной PostgreSQL-транзакции

Статус: принято для демонстрационного MVP.

## Контекст

Нужно предотвратить отрицательные остатки и повторное проведение при конкурентных запросах и повторной доставке. Нельзя зависеть от доступности брокера в момент HTTP-команды.

## Решение

Модульный монолит, PostgreSQL READ COMMITTED, блокировка строк счетов в стабильном порядке, advisory lock ключа идемпотентности. Неизменяемые проводки и текущие остатки сохраняются вместе с Operation и Outbox. Worker доставляет через MassTransit и RabbitMQ; Inbox фиксирует эффект один раз. DTO отделены от EF сущностей для команд движения. Для небольших read endpoints используются проекции EF без repository.

## Альтернативы

- Только optimistic concurrency: возможна, но требует пересчёта и retry; сложнее защищать создание первой позиции.
- SERIALIZABLE: надёжно, но нужны повторы serialization failure, более широкие конфликты.
- Redis lock: лишняя инфраструктура и отдельная область отказа.
- RabbitMQ как журнал остатков: не даёт нужной атомарности с PostgreSQL.
- Микросервисы: неоправданно усложняют согласованность маленькой модели.
- Встроенный MassTransit EF Outbox: разумное production-направление; собственный небольшой dispatcher выбран для прозрачности демонстрации.

## Последствия

Простая проверяемая модель с уменьшенной пропускной способностью на горячем счёте. Доставка повторяема, consumer обязан быть идемпотентным. Историческая оценка использует журнал, а не текущий остаток. Обновление схемы пока ручное: переход на EF migrations обязателен перед развитием с сохранением существующих данных.
